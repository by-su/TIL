# TypeScript는 왜 만들어졌는가 ? 

## 배경
- JavaScript라는 언어는 브라우저에서 가볍게 사용하도록 설정된 언어. 하지만 코드베이스가 급격히 커지면서 다음과 같은 문제 발생.
    - 타입 없음: `function process(data)` 이게 string인지 object인지 런타임까지 가봐야 알 수 있음
    - 인터페이스 계약 없음: API응답 구조를 바꾸면 쓰는 쪽에서 조용히 깨짐. 컴파일 타임에 잡을 수 있는 에러가 전부 프로덕션에서 발생.

## 등장
- JavaScript 코드를 한 줄도 안 바꾸고 그대로 쓸 수 있는 Superset
    - .js -> .ts로 확장자만 바꿔도 유효한 TypeScript가 됨.
    - 전체 마이그레이션 없이 파일 하나씩 점진적으로 타입을 입힐 수 있음.
    - `any`로 시작해서 점점 strict하게 가는 게 가능

## 설계 철학
- TypeScript의 타입 시스템은 soundness(건정성)보다 실용성을 택함.
    - 100% 타입 안전을 보장하지 않음. `any`도 있고, type assertion도 있음. 
    - 의도적으로 escape hatch를 열어둔 구조
```typescript
// 1. any — 타입 검사를 아예 끔
const data: any = "hello";
const num: number = data; // 컴파일 에러 없음. 런타임에서도 안 터짐(이번엔 운 좋게)

// 2. type assertion — 개발자가 "나를 믿어"라고 강제
const input = document.getElementById("name") as HTMLInputElement;
// 실제로는 null일 수도 있는데, 컴파일러는 HTMLInputElement라고 믿어버림

// 3. 구조적 타이핑의 허점
function getLength(arr: string[]) {
    return arr.length;
}
const tuple: [string, string] = ["a", "b"];
getLength(tuple); // OK — 근데 tuple에 push하면 타입 시스템이 못 잡는 케이스 생김
```

## 정리
- 해결한 문제: 대규모 JavaScript 코드베이스의 유지보수성.
- 타입 시스템 -> 컴파일 타임에 에러를 잡아주고, IDE가 코드를 이해할 수 있게 됨 -> 자동완성, 리팩토링, 네비게이션이 좋아짐
- 결국 JavaScript로 트랜스파일되기 때문에 런타임에 영향 없음.
