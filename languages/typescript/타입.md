## TypeScript 타입 총정리 — 원시 타입부터 특수 타입까지

### 왜 타입을 알아야 하나?

TypeScript를 쓰는 이유는 변수에 어떤 값이 들어올 수 있는지 **컴파일 시점에 제한**하기 위해서다. 그 출발점이 기본 타입이며, 여기서 배열, 객체, 특수 타입으로 확장된다.

### 타입 체계 도식도

TypeScript의 주요 타입이 어떤 계층으로 구성되는지 한눈에 보면 다음과 같다.

```
TypeScript 타입
├── 원시 타입 (Primitive)
│   ├── number
│   ├── string
│   ├── boolean
│   ├── null
│   └── undefined
│
├── 리터럴 타입 (Literal)
│   ├── 숫자 리터럴    (예: 10)
│   ├── 문자열 리터럴   (예: "hello")
│   └── 불리언 리터럴   (예: true)
│
├── 복합 타입
│   ├── 배열           number[], Array<string>
│   ├── 튜플           [number, string] — 길이·위치별 타입 고정
│   ├── 객체 리터럴 타입  { id: number; name: string }
│   │   ├── 선택적 프로퍼티   id?: number
│   │   └── readonly 프로퍼티  readonly apiKey: string
│   ├── 타입 별칭       type User = { ... }
│   ├── 인덱스 시그니처   { [key: string]: string }
│   └── enum           enum Role { ADMIN, USER }
│
├── 대수 타입 (Algebraic)
│   ├── 합집합 (Union)       string | number — 둘 중 하나
│   └── 교집합 (Intersection) Dog & Person — 둘 다 만족
│
└── 특수 타입
    ├── any            타입 검사 포기 (지양)
    ├── unknown        안전한 any — 타입 좁히기 필요
    ├── void           반환값 없음
    └── never          반환 자체가 불가능
```

---

### 원시 타입 (Primitive Type)

원시 타입은 **하나의 값만 저장**하는 타입이다. `number`, `string`, `boolean`, `null`, `undefined` 다섯 가지가 있다.

`number` 타입은 일반적인 숫자 외에 특수 값도 포함한다.

```typescript
let num1: number = Infinity;
let num2: number = -Infinity;
let num3: number = NaN;          // 이 셋 모두 number 타입에 속한다
```

#### null 할당이 필요할 때

기본 설정에서는 `number` 타입에 `null`을 할당할 수 없다.

```typescript
let numA: number = null;  // ❌ 기본 설정에서는 에러
```

`tsconfig.json`에서 `strictNullChecks`를 `false`로 설정하면 허용된다. 단, 프로젝트 전체에서 null 안전성 검사가 비활성화되므로 주의가 필요하다.

---

### 리터럴 타입 (Literal Type)

리터럴 타입은 **특정 값 자체**를 타입으로 사용하는 것이다. "리터럴 = 값"이라고 생각하면 된다.

```typescript
let numA: 10 = 10;
numA = 12;  // ❌ 에러 — 타입이 10이므로 10만 할당 가능
```

`number`는 "아무 숫자나 가능"이지만, `10`은 "오직 10만 가능"이다. 타입의 범위를 극단적으로 좁히는 방식이다.

#### 리터럴 타입은 언제 쓰나?

단독으로는 쓸모가 제한적이지만, **유니온 타입**과 결합하면 허용 가능한 값의 목록을 정의할 수 있다.

```typescript
type Direction = "up" | "down" | "left" | "right";

let move: Direction = "up";         // ✅
let wrong: Direction = "diagonal";  // ❌ 네 가지 중 하나만 가능
```

---

### 배열

배열 타입을 선언하는 두 가지 방식이 있다.

```typescript
// 1번 방식: 타입[]
let numArr: number[] = [1, 2, 3];
let strArr: string[] = ["hello", "world"];

// 2번 방식: Array<타입> (제네릭)
let boolArr: Array<boolean> = [true, false, true];
```

요소의 타입이 여러 가지라면 유니온 타입을 사용한다.

```typescript
let multiArr: (number | string)[] = [1, "hello"];
```

다차원 배열은 `[]`를 중첩한다.

```typescript
let doubleArr: number[][] = [
  [1, 2, 3],
  [4, 5],
];
```

---

### 튜플 (Tuple)

튜플은 **길이와 각 위치의 타입이 고정된 배열**이다. 일반 배열과 달리 "몇 번째에 어떤 타입이 오는지"를 지정할 수 있다.

```typescript
let tup1: [number, number] = [1, 2];
let tup2: [number, string, boolean] = [1, "2", true];
```

컴파일된 JavaScript에서는 일반 배열로 변환된다. 튜플은 TypeScript에서만 존재하는 개념이다.

```javascript
// 컴파일 결과
let tup1 = [1, 2];
let tup2 = [1, "2", true];
```

---

### 객체

#### `object` 타입의 한계

`object`로 타입을 명시하면 "이건 객체다"라는 것만 알려줄 뿐, 내부 프로퍼티에 접근할 수 없다.

```typescript
let user: object = {
  id: 1,
  name: "bysu",
};

user.id;  // ❌ 에러 — object 타입은 프로퍼티 정보를 모른다
```

#### 객체 리터럴 타입

프로퍼티의 타입까지 명시하면 안전하게 접근할 수 있다. 이를 **객체 리터럴 타입**이라 한다.

```typescript
let user: {
  id: number;
  name: string;
} = {
  id: 1,
  name: "bysu",
};

user.id;  // ✅ 접근 가능
```

#### 선택적 프로퍼티 (`?`)

특정 프로퍼티가 없어도 되는 경우 `?`를 붙인다.

```typescript
let user: {
  id?: number;    // 있어도 되고 없어도 됨
  name: string;
} = {
  name: "bysu",  // ✅ id 없이도 가능
};
```

#### 읽기 전용 프로퍼티 (`readonly`)

값이 수정되면 안 되는 프로퍼티에는 `readonly`를 붙인다.

```typescript
let config: {
  readonly apiKey: string;
} = {
  apiKey: "MY API KEY",
};

config.apiKey = "fu";  // ❌ 에러 — readonly 프로퍼티는 수정 불가
```

---

### 타입 별칭 (Type Alias)

같은 객체 구조를 여러 변수에 반복 작성하는 건 비효율적이다. `type` 키워드로 이름을 붙여 재사용할 수 있다.

```typescript
type User = {
  id: number;
  name: string;
};

let user: User = {
  id: 1,
  name: "bysu",
};

let user2: User = {
  id: 2,
  name: "someone",
};
```

---

### 인덱스 시그니처 (Index Signature)

프로퍼티의 key와 value가 일정한 규칙을 따를 때, 모든 프로퍼티를 일일이 나열하지 않고 **규칙 자체를 타입으로 정의**하는 방식이다.

```typescript
// 모든 key가 string, 모든 value도 string인 객체
type CountryCodes = {
  [key: string]: string;
};

let countryCodes: CountryCodes = {
  Korea: "ko",
  UnitedState: "us",
  Japan: "jp",
  // 얼마든지 추가 가능
};
```

특정 프로퍼티를 필수로 강제하고 싶다면 함께 명시한다.

```typescript
type CountryCodes = {
  [key: string]: string;
  Korea: string;           // Korea는 반드시 있어야 함
};
```

---

### enum 타입

관련된 상수를 하나의 그룹으로 묶을 때 사용한다.

```typescript
enum Role {
  ADMIN = 0,
  USER = 1,
  GUEST = 2,
}

const user1 = {
  name: "bysu",
  role: Role.ADMIN,  // 0
};
```

enum은 컴파일해도 사라지지 않고 **JavaScript 객체로 변환**된다. 이 점이 `type`이나 `interface`와 다르다.

### any와 unknown

#### `any` — 타입 검사 포기

어떤 타입이든 할당할 수 있고, 어디에든 넣을 수 있다. 사실상 타입 검사를 하지 않으므로 TypeScript를 사용하는 의미가 사라진다. **최대한 지양**해야 한다.

#### `unknown` — 안전한 any

`any`처럼 아무 값이나 넣을 수 있지만, 다른 타입 변수에 바로 할당할 수 없다.

```typescript
let unknownVar: unknown;

let num: number = 10;
num = unknownVar;  // ❌ 에러 — unknown을 number에 바로 넣을 수 없다
```

**타입 좁히기(type narrowing)**를 거쳐야 사용할 수 있다.

```typescript
if (typeof unknownVar === "number") {
  num = unknownVar;  // ✅ 타입이 확인되었으므로 가능
}
```

`any`보다 `unknown`을 사용하면 실수로 타입이 섞이는 것을 방지할 수 있다.

#### `unknown`은 타입 캐스팅을 무시한다

`unknown`은 TypeScript 타입 계층에서 특이한 위치에 있다. `never`를 제외한 모든 타입과의 캐스팅이 자유롭다.

```
unknown (전체 집합)
  ↑ 업캐스팅: 모든 타입 → unknown  ✅
  ↓ 다운캐스팅: unknown → 모든 타입  ✅ (as 사용)
  ✗ 예외: unknown → never           ❌ (never는 공집합이라 불가)
```

모든 타입의 값을 `unknown`에 넣을 수 있고(업캐스팅), `unknown`을 `as`로 특정 타입으로 단언할 수도 있다(다운캐스팅).

```typescript
// 업캐스팅 — 어떤 타입이든 unknown에 넣을 수 있다
let a: unknown = 123;         // number → unknown  ✅
let b: unknown = "hello";     // string → unknown  ✅
let c: unknown = true;        // boolean → unknown ✅

// 다운캐스팅 — as를 사용하면 unknown을 특정 타입으로 단언할 수 있다
let num: number = a as number;      // unknown → number  ✅
let str: string = b as string;      // unknown → string  ✅

// never만 예외 — never는 어떤 값도 가질 수 없는 공집합이다
let nev: never = a as never;        // ❌ unknown → never는 불가
```

`any`도 캐스팅이 자유롭지만, `any`는 타입 검사 자체를 꺼버린다. 반면 `unknown`은 **캐스팅은 허용하되, 직접 사용할 때는 타입 좁히기를 강제**한다는 점이 다르다. "일단 받아들이되, 쓸 때는 확인하라"는 원칙이다.

---

### void와 never

#### `void` — 반환값이 없음

함수가 아무것도 반환하지 않을 때 사용한다.

```typescript
function log(msg: string): void {
  console.log(msg);
}
```

#### `never` — 반환이 불가능함

함수가 정상적으로 종료될 수 없는 경우에 사용한다. `void`는 "반환값이 없다"이고, `never`는 "반환 자체가 불가능하다"이다.

```typescript
// 무한 루프 — 함수가 끝나지 않는다
function infinite(): never {
  while (true) {}
}

// 항상 에러를 던짐 — 정상 반환이 불가능하다
function throwError(): never {
  throw new Error("에러 발생");
}
```

### 대수 타입 (Algebraic Type)

대수 타입은 **여러 개의 타입을 합성해서 새로운 타입을 만들어내는 방식**이다. 수학의 집합 연산처럼, 합집합(Union)과 교집합(Intersection) 두 가지가 있다.

#### 합집합 타입 (Union Type) — `|`

`|`로 연결하면 "이 중 하나"를 의미한다. 변수가 여러 타입의 값을 가질 수 있을 때 사용한다.

```typescript
let a: string | number;

a = 1;        // ✅ number
a = "hello";  // ✅ string
```

객체 타입의 유니온은 조금 더 주의가 필요하다. 다음 두 타입을 보자.

```typescript
type Dog = {
  name: string;
  color: string;
};

type Person = {
  name: string;
  language: string;
};

type Union1 = Dog | Person;
```

`Union1`은 `Dog`이거나 `Person`이면 된다. 어떤 객체가 이 유니온에 속하려면, **Dog 또는 Person 중 최소 하나의 조건을 완전히 만족**해야 한다.

```typescript
// ✅ Dog의 모든 프로퍼티를 충족
let union1: Union1 = {
  name: "",
  color: "",
};

// ✅ Person의 모든 프로퍼티를 충족
let union2: Union1 = {
  name: "",
  language: "",
};

// ✅ Dog와 Person 모두 충족 — 둘 다 만족해도 된다
let union3: Union1 = {
  name: "",
  color: "",
  language: "",
};

// ❌ 에러 — Dog도 Person도 완전히 충족하지 못한다
// Dog이려면 color가 필요하고, Person이려면 language가 필요하다
let union4: Union1 = {
  name: "",
};
```

핵심은 "둘 중 하나를 **완전히** 만족해야 한다"는 점이다. 공통 프로퍼티만 가지고는 어느 쪽도 충족할 수 없다.

#### 교집합 타입 (Intersection Type) — `&`

`&`로 연결하면 "이것도 저것도 모두 만족"을 의미한다.

원시 타입끼리 교집합을 만들면, 동시에 두 타입일 수 있는 값은 없으므로 `never`가 된다.

```typescript
let variable: number & string;
// → never 타입 — number이면서 동시에 string인 값은 존재하지 않는다
```

교집합 타입이 실제로 유용한 건 **객체 타입**을 결합할 때다. 두 타입의 프로퍼티를 모두 가진 하나의 타입을 만든다.

```typescript
type Intersection = Dog & Person;

// Dog의 프로퍼티(name, color) + Person의 프로퍼티(name, language) 모두 필요
let intersection1: Intersection = {
  name: "",
  color: "",
  language: "",
};

// ❌ 에러 — 하나의 프로퍼티라도 빠지면 타입 에러 발생
```

#### Union vs Intersection 한눈에 비교

```
Union (합집합) A | B          Intersection (교집합) A & B
┌─────────┐                  ┌─────────┐
│    A    ╱│                  │    A    │
│      ╱  │                  │  ┌───┐  │
│   ╱     │  ← 어느 한쪽만   │  │A&B│  │  ← 양쪽 모두
│ ╱    B  │     충족하면 OK   │  └───┘  │     충족해야 OK
│╱        │                  │    B    │
└─────────┘                  └─────────┘
```

| | Union (`\|`) | Intersection (`&`) |
|---|---|---|
| 의미 | A **또는** B | A **그리고** B |
| 객체 프로퍼티 | 한쪽만 만족하면 됨 | 양쪽 모두 만족해야 함 |
| 원시 타입 조합 | `string \| number` → 유용 | `string & number` → `never` |

---

### 정리

| 분류 | 타입 | 핵심 |
|---|---|---|
| 원시 | `number`, `string`, `boolean`, `null`, `undefined` | 하나의 값을 저장 |
| 리터럴 | `10`, `"hello"`, `true` | 특정 값만 허용 |
| 배열/튜플 | `number[]`, `[number, string]` | 튜플은 위치별 타입 고정 |
| 객체 | 객체 리터럴 타입, 타입 별칭 | `?`로 선택, `readonly`로 보호 |
| 인덱스 시그니처 | `[key: string]: string` | key-value 규칙 정의 |
| enum | `enum Role { ... }` | JS 객체로 컴파일됨 |
| 대수 | `A \| B` (Union), `A & B` (Intersection) | 합집합은 하나만, 교집합은 모두 만족 |
| 특수 | `any` < `unknown` < 구체 타입 | unknown이 any보다 안전 |
| 반환 | `void` vs `never` | 반환 없음 vs 반환 불가능 |

### 타입 추론 (Type Inference)

TypeScript는 모든 변수에 타입을 명시하지 않아도 **초기값을 보고 타입을 자동으로 추론**한다. 매번 `: number`, `: string`을 붙이지 않아도 되는 이유가 바로 이 기능 덕분이다.

단, 모든 상황에서 정확하게 추론하지는 못한다. 어떤 경우에 잘 추론하고, 어떤 경우에 문제가 되는지를 아는 것이 중요하다.

#### 변수: 초기값 기준으로 추론

변수를 선언하면서 값을 할당하면, TypeScript는 그 값의 타입을 변수의 타입으로 사용한다.

```typescript
let a = 10;       // number로 추론
let b = "hello";  // string으로 추론
```

타입을 직접 쓰지 않았지만, `a`에 문자열을 넣으면 에러가 발생한다. 초기값 `10`으로부터 `number` 타입이 결정되었기 때문이다.

#### 함수: 반환값 기준으로 추론

함수의 반환 타입도 명시하지 않으면 `return` 문의 값을 보고 추론한다.

```typescript
function func() {
  return "hello";
}
// 반환 타입이 string으로 추론됨
```

#### 초기값이 없으면? — 암묵적 `any`와 `any`의 진화

초기값 없이 변수만 선언하면 추론할 근거가 없으므로 `any` 타입이 된다. 이를 **암묵적 any**(implicit any)라고 한다.

```typescript
let d;  // any로 추론 — 아무 값이나 넣을 수 있다
```

흥미로운 점은 이 `any`가 값이 할당될 때마다 **해당 시점의 타입으로 변한다**는 것이다. 이 현상을 **any의 진화**(evolving any)라고 부른다.

```typescript
let d;            // any

d = 10;           // 이 시점부터 number로 추론
d.toFixed();      // ✅ number 메서드 — 사용 가능
d.toUpperCase();  // ❌ 에러 — number에는 toUpperCase가 없다

d = "hello";      // 이 시점부터 string으로 추론
d.toUpperCase();  // ✅ string 메서드 — 사용 가능
d.toFixed();      // ❌ 에러 — string에는 toFixed가 없다
```

할당되는 값에 따라 타입이 계속 바뀌므로, 코드의 **위치에 따라 같은 변수의 타입이 달라진다**.

#### `let` vs `const` — 추론 범위가 다르다

`let`은 값이 변할 수 있으므로 **넓은 타입**(원시 타입)으로 추론하지만, `const`는 값이 바뀔 수 없으므로 **리터럴 타입**으로 추론한다.

```typescript
let num = 10;       // number로 추론 — 나중에 다른 숫자를 넣을 수 있으니까
const NUM = 10;     // 10 (리터럴 타입)으로 추론 — 값이 절대 바뀌지 않으니까

let str = "hello";    // string으로 추론
const STR = "hello";  // "hello" (리터럴 타입)으로 추론
```

`const`는 재할당이 불가능하므로 "이 변수는 정확히 이 값이다"라고 단언할 수 있다. 그래서 `number`가 아니라 `10`, `string`이 아니라 `"hello"`로 좁혀진다.

#### 배열: 요소들의 유니온 타입

여러 타입의 값이 섞인 배열은 **유니온 타입 배열**로 추론된다.

```typescript
let arr = [1, "string"];  // (number | string)[]로 추론
```

TypeScript가 배열의 모든 요소를 확인한 뒤, 가능한 타입들을 `|`로 합친 결과를 배열의 타입으로 결정한다.

#### 타입 추론 정리

| 상황 | 추론 결과 | 예시 |
|---|---|---|
| `let` + 초기값 | 초기값의 원시 타입 | `let a = 10` → `number` |
| `const` + 초기값 | 리터럴 타입 | `const a = 10` → `10` |
| 함수 반환 | `return` 값의 타입 | `return "hi"` → `string` |
| 초기값 없는 `let` | `any` (암묵적) | `let d` → `any` |
| 혼합 배열 | 유니온 타입 배열 | `[1, "a"]` → `(number \| string)[]` |

### 타입 단언 (Type Assertion)

TypeScript가 타입을 추론하지 못하거나, 개발자가 타입을 더 정확히 알고 있을 때 **"이 값은 이 타입이야"라고 직접 알려주는 방식**이다.

#### 왜 필요한가?

빈 객체를 만들고 나중에 프로퍼티를 채우는 패턴을 생각해 보자.

```typescript
type Person = {
  name: string;
  age: number;
};

let person = {};
person.name = "bysu";  // ❌ 에러 — {}에는 name 프로퍼티가 없다
person.age = 1;         // ❌ 에러 — {}에는 age 프로퍼티가 없다
```

TypeScript는 `person`을 `{}` 타입으로 추론했기 때문에, 프로퍼티에 접근하면 에러가 발생한다. 그렇다고 타입을 직접 명시하면 이번에는 초기값이 조건을 만족하지 못한다.

```typescript
let person: Person = {};  // ❌ 에러 — name과 age가 필수인데 비어 있다
```

이럴 때 `as`로 타입 단언을 사용한다.

```typescript
let person = {} as Person;  // ✅ "이 빈 객체는 Person 타입으로 취급해줘"

person.name = "bysu";  // ✅
person.age = 1;         // ✅
```

#### 초과 프로퍼티도 허용된다

타입 단언을 사용하면 타입에 정의되지 않은 프로퍼티가 있어도 에러가 발생하지 않는다.

```typescript
type Dog = {
  name: string;
  color: string;
};

let dog = {
  name: "bysu",
  color: "brown",
  breed: "human",    // Dog에 없는 프로퍼티지만 에러 없음
} as Dog;
```

타입 단언은 TypeScript의 타입 검사를 개발자가 **의도적으로 우회**하는 것이므로, 초과 프로퍼티 검사도 건너뛴다. 편리하지만 그만큼 **잘못된 타입 단언은 런타임 오류로 이어질 수 있다**.

#### 타입 단언의 규칙 — `A as B`

아무 타입이나 단언할 수 있는 것은 아니다. `A as B`가 성립하려면 다음 중 하나를 만족해야 한다.

- **A가 B의 슈퍼타입**이거나 (다운캐스팅)
- **A가 B의 서브타입**이어야 한다 (업캐스팅)

즉, A와 B 사이에 **상하 관계**가 있어야 한다. 아무 관련 없는 타입끼리는 단언할 수 없다.

```typescript
let num = 10 as string;  // ❌ 에러 — number와 string은 상하 관계가 아니다
```

#### `const` 단언 — `as const`

`let` 변수에 `as const`를 붙이면 `const`로 선언한 것과 동일하게 **리터럴 타입**으로 추론된다.

```typescript
let num4 = 10 as const;  // 10 리터럴 타입 (number가 아님)
```

객체에 `as const`를 붙이면 **모든 프로퍼티가 `readonly`**가 된다.

```typescript
let cat = {
  name: "야옹이",
  color: "yellow",
} as const;

cat.name = "";  // ❌ 에러 — readonly 프로퍼티는 수정 불가
```

`as const`가 적용된 객체는 모든 프로퍼티가 리터럴 타입 + `readonly`로 잠긴다. 설정 객체처럼 변하지 않아야 하는 값에 유용하다.

#### Non-null 단언 — `!`

옵셔널 프로퍼티를 다룰 때 흔히 마주치는 상황을 보자.

```typescript
type Post = {
  title: string;
  author?: string;  // string | undefined
};

let post: Post = {
  title: "1",
  author: "bysu",
};
```

`author`는 옵셔널이므로 `string | undefined`가 된다. 옵셔널 체이닝(`?.`)으로 안전하게 접근할 수 있지만, 반환 타입도 `undefined`를 포함하게 된다.

```typescript
const len: number = post.author?.length;
// ❌ 에러 — post.author?.length의 타입은 number | undefined
// number 타입 변수에 담을 수 없다
```

옵셔널 체이닝(`?.`)은 값이 `null` 또는 `undefined`이면 뒤의 프로퍼티 접근 없이 **전체 표현식이 `undefined`를 반환**한다. 그래서 결과 타입이 `number | undefined`가 되어 `number` 변수에 할당할 수 없다.

`author`가 확실히 존재한다고 알고 있다면, `!`(non-null 단언 연산자)로 `null`과 `undefined`를 제거할 수 있다.

```typescript
const len: number = post.author!.length;  // ✅ "author는 반드시 존재해"
```

`!`는 TypeScript에게 "이 값은 `null`이나 `undefined`가 아니다"라고 단언하는 것이다. 실제로 값이 없으면 **런타임 에러가 발생**하므로, 값이 존재한다는 확신이 있을 때만 사용해야 한다.

#### 타입 단언 정리

| 종류 | 문법 | 용도 |
|---|---|---|
| 기본 단언 | `값 as 타입` | 개발자가 타입을 직접 지정 |
| `const` 단언 | `값 as const` | 리터럴 타입 + `readonly` 적용 |
| Non-null 단언 | `값!` | `null \| undefined` 가능성 제거 |

> **주의**: 타입 단언은 TypeScript의 타입 검사를 개발자가 직접 우회하는 것이다. 단언이 틀리면 컴파일러는 잡아주지 못하고, 런타임에서야 오류가 드러난다. 가능하면 타입 좁히기(type narrowing)를 먼저 시도하고, 단언은 최후의 수단으로 사용하자.

### 타입 좁히기 (Type Narrowing)

유니온 타입은 편리하지만, 실제로 값을 **사용**하려면 문제가 생긴다. `string | number` 타입의 변수에서 `.toUpperCase()`를 호출할 수 있을까?

```typescript
function process(value: string | number) {
  value.toUpperCase();  // ❌ 에러 — number일 수도 있으니 허용 불가
}
```

TypeScript는 "혹시 number일 수도 있잖아"라고 막는다. 이때 **조건문으로 타입의 범위를 좁혀주면** 안전하게 사용할 수 있다. 이것이 **타입 좁히기(Type Narrowing)**다.

```typescript
function process(value: string | number) {
  if (typeof value === "string") {
    // 이 블록 안에서 value는 string 확정
    value.toUpperCase();  // ✅
  } else {
    // 여기서 value는 number 확정
    value.toFixed();      // ✅
  }
}
```

조건문을 통과하면 TypeScript가 자동으로 타입을 좁혀준다. 개발자가 `as`로 강제하는 타입 단언과 달리, **컴파일러가 직접 추론**하므로 안전하다.

#### 타입 좁히기의 흐름

```
string | number  (넓은 타입)
       │
  typeof === "string" ?
      ├── Yes → string     (좁혀진 타입)
      └── No  → number     (좁혀진 타입)
```

### 타입 가드 (Type Guard)

타입 좁히기를 **수행하는 조건식** 자체를 타입 가드라고 부른다. TypeScript가 인식하는 타입 가드에는 여러 종류가 있다.

#### 1. `typeof` — 원시 타입 구별

가장 기본적인 타입 가드다. `string`, `number`, `boolean`, `undefined`, `object`, `function` 등을 구별할 수 있다.

```typescript
function printLength(value: string | number) {
  if (typeof value === "string") {
    console.log(value.length);  // ✅ string으로 좁혀짐
  }
}
```

단, `typeof null`은 `"object"`를 반환하므로 null 체크에는 사용할 수 없다.

#### 2. `instanceof` — 클래스 인스턴스 구별

객체가 특정 클래스의 인스턴스인지 확인할 때 사용한다.

```typescript
class Dog {
  bark() { console.log("멍!"); }
}

class Cat {
  meow() { console.log("야옹!"); }
}

function speak(animal: Dog | Cat) {
  if (animal instanceof Dog) {
    animal.bark();  // ✅ Dog로 좁혀짐
  } else {
    animal.meow();  // ✅ Cat으로 좁혀짐
  }
}
```

`typeof`는 원시 타입을, `instanceof`는 클래스 인스턴스를 구별한다고 기억하면 된다.

#### 3. `in` 연산자 — 프로퍼티 존재 여부로 구별

특정 프로퍼티가 객체에 존재하는지 확인하여 타입을 좁힌다. 클래스가 아닌 **일반 객체 타입**을 구별할 때 유용하다.

```typescript
type Fish = { swim: () => void };
type Bird = { fly: () => void };

function move(animal: Fish | Bird) {
  if ("swim" in animal) {
    animal.swim();  // ✅ Fish로 좁혀짐
  } else {
    animal.fly();   // ✅ Bird로 좁혀짐
  }
}
```

#### 4. 리터럴 타입 + 판별 프로퍼티 — 서로소 유니온

객체 유니온에서 가장 강력한 패턴이다. 각 타입에 **고유한 리터럴 값을 가진 공통 프로퍼티**를 두면, 그 값만으로 타입을 확정할 수 있다.

```typescript
type Circle = {
  kind: "circle";    // 판별 프로퍼티 — 리터럴 타입
  radius: number;
};

type Rectangle = {
  kind: "rectangle";  // 판별 프로퍼티 — 리터럴 타입
  width: number;
  height: number;
};

type Shape = Circle | Rectangle;
```

`kind` 프로퍼티의 값이 `"circle"`과 `"rectangle"`로 겹치지 않으므로(서로소), `kind`만 확인하면 타입이 확정된다.

```typescript
function getArea(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      // Circle로 좁혀짐 — radius 접근 가능
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      // Rectangle로 좁혀짐 — width, height 접근 가능
      return shape.width * shape.height;
  }
}
```

이 패턴을 **서로소 유니온(Discriminated Union)** 또는 **태그드 유니온(Tagged Union)**이라 부른다. 실무에서 가장 자주 쓰이는 타입 좁히기 패턴이다.

#### 5. 사용자 정의 타입 가드 — `is` 키워드

위 방법으로 해결이 안 될 때, **함수의 반환 타입에 `is`를 써서** 직접 타입 가드를 만들 수 있다.

```typescript
type Dog = { name: string; isBark: boolean };
type Cat = { name: string; isScratch: boolean };

// 반환 타입이 `animal is Dog` — "true를 반환하면 animal은 Dog다"라는 의미
function isDog(animal: Dog | Cat): animal is Dog {
  return "isBark" in animal;
}
```

이 함수를 조건문에 사용하면 TypeScript가 타입을 좁혀준다.

```typescript
function greeting(animal: Dog | Cat) {
  if (isDog(animal)) {
    // Dog로 좁혀짐
    console.log(`${animal.name}가 짖는다: ${animal.isBark}`);
  } else {
    // Cat으로 좁혀짐
    console.log(`${animal.name}가 할퀸다: ${animal.isScratch}`);
  }
}
```

`is` 없이 `boolean`만 반환하면 TypeScript는 타입을 좁히지 못한다. `is`가 "이 함수가 true를 반환하면 매개변수는 이 타입이다"라는 **계약**을 컴파일러에 알려주는 역할을 한다.

#### 타입 가드 선택 기준

| 상황 | 타입 가드 | 예시 |
|---|---|---|
| 원시 타입 구별 | `typeof` | `string \| number` |
| 클래스 인스턴스 구별 | `instanceof` | `Date \| Error` |
| 프로퍼티 유무로 구별 | `in` | `Fish \| Bird` |
| 리터럴 판별값이 있는 객체 | 서로소 유니온 | `{ kind: "circle" } \| { kind: "rect" }` |
| 위 방법으로 부족할 때 | `is` (사용자 정의) | 복잡한 조건의 커스텀 판별 |

### 타입 좁히기 vs 타입 단언

둘 다 "넓은 타입을 좁히는" 행위지만, **안전성이 다르다**.

```
타입 좁히기 (Narrowing)          타입 단언 (Assertion)
┌─────────────────────┐        ┌─────────────────────┐
│ 컴파일러가 검증한다     │        │ 개발자가 선언한다      │
│ 런타임 조건문 기반      │        │ 런타임 검사 없음       │
│ 안전하다               │        │ 틀리면 런타임 에러     │
└─────────────────────┘        └─────────────────────┘
```

가능하면 **타입 좁히기를 먼저 시도**하고, 좁히기로 해결할 수 없는 경우(예: 빈 객체 초기화)에만 타입 단언을 사용하는 것이 원칙이다.
